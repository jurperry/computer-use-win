### 幻灯片 3 / PDF 第 3 页 — SIZE MODEL：三种尺寸：物理、逻辑、截图

- 导语：`同一块 2560×1440 @150% 的屏幕，三个数字同时存在，但 CU 只用其中两套。`
- 三栏并置：

  **① 物理像素**
  - `2560 × 1440`
  - `SetCursorPos`
  - `CopyFromScreen`
  - `WindowFromPoint`
  - `唯一真值`

  **② Windows 逻辑像素**
  - `≈ 1707 × 960`
  - `150% 缩放后的桌面坐标`
  - `CU 不使用`
  - `误传给 SetCursorPos 会点偏`
  - `仅存在于未声明 PMv2 的进程`

  **③ 模型看到的截图**
  - `1456 × 819`
  - `长边 ≤ 1568`
  - `token 预算 ≤ 1568`
  - `比例 1.758242`
  - `不是 2560 ÷ 1.5`

- 坐标公式（原文两行，居中突出）：

  ```text
  screenX = round(imageX × displayWidth / imageWidth) + originX
  screenY = round(imageY × displayHeight / imageHeight) + originY
  ```

- 脚注：`1456×819 不是 1568×882：56×32 = 1792，超过 1568 的 token 预算。`

### 幻灯片 4 / PDF 第 4 页 — FULL DISPLAY：整屏模式：从屏幕到点击

- 导语：`CopyFromScreen 取当前显示器整块物理画面；坐标原点就是显示器左上角。`
- 示意图（左右两个方框 + 中间缩放箭头）：
  - 左：`物理屏幕 2560×1440`，`origin (0,0)`，标注点 `物理 (1280, 721)`
  - 中：`× 1.758`
  - 右：`模型截图 1456×819`，`origin (0,0)`，标注点 `图像 (728, 410)`
- 计算过程（逐步相消）：

  ```text
  screenX = round(728 × 2560 / 1456) + 0 = 1280
  screenY = round(410 × 1440 / 819) + 0 = 721
  ```

- 注意：`origin 来自截图当时的显示器 Bounds；副屏可以为负。`

### 幻灯片 5 / PDF 第 5 页 — BOUND WINDOW：绑定窗口：1920×1080 只是示例

- 导语：`绑定截图取当前窗口的物理矩形；窗口多大就截多大，不存在固定 1920×1080。`
- 对照表：

  | 窗口情况 | GetWindowRect 物理矩形 | 绑定截图 |
  | --- | --- | --- |
  | 1280×720 @100% | 1280×720 | 1280×720 |
  | 应用认为 1280×720 @150% | 1920×1080 | 1456×819 |
  | 最大化 2560×1440 | 2560×1440 | 1456×819 |
  | 小窗口 800×600 | 800×600 | 800×600 |

- 三条要点：
  - `• 每次截图重新读 GetWindowRect；窗口可缩放、最大化、跨屏。`
  - `• 普通窗口还包含标题栏/边框，客户区更小；游戏无边框时通常就是整个画面。`
  - `• 1920×1080 = 1280×720 × 1.5，只是示例，不是绑定模式的固定尺寸。`

### 幻灯片 6 / PDF 第 6 页 — BOUND WINDOW：绑定模式：从窗口到点击

- 导语：`窗口截图是窗口局部坐标；最后只加一次 GetWindowRect 的窗口原点。`
- 示意图：
  - 左：`窗口物理矩形 1920×1080`，`origin (0,0) 窗口左上`，标注点 `窗口局部 (960, 541)`
  - 中：`× 1.318`
  - 右：`模型截图 1456×819`，`origin (0,0)`，标注点 `图像 (728, 410)`
- 计算过程（先窗口局部、再加一次原点）：

  ```text
  windowX = round(728 × 1920 / 1456) = 960
  windowY = round(410 × 1080 / 819) = 541
  screen = (960 + 320, 541 + 180) = (1280, 721)
  ```

- 注意：`displayWidth 是窗口输入表面 1920，不是显示器 2560；窗口原点只加一次。`

### 幻灯片 7 / PDF 第 7 页 — CAPTURE STACK：PMv2、PrintWindow、DWM：各管一层

- 导语：`把「尺子、画笔、投影仪」分开，很多困惑就消失了。`
- 三分层表：

  | 层 | 是什么 | 控制什么 | 不是什么 |
  | --- | --- | --- | --- |
  | PMv2 | 调用进程的 DPI 感知模式 | 调用者拿到逻辑还是物理坐标 | 不是截图 API；不读图 |
  | PrintWindow | 窗口捕获 API | 让目标窗口往给定 DC 画什么 | 不读 DWM 最终合成 |
  | DWM | 桌面合成器 | 窗口最终在屏幕上的缩放/合成 | 不在 PrintWindow 路径里 |

- 三个比喻标签（横向排列）：`PMv2 = 尺子` / `PrintWindow = 画笔` / `DWM = 投影仪`
- 边界强调：`PMv2 不读图；PrintWindow 不读 DWM 输出；DWM 不参与 PrintWindow 的绘制。`

### 幻灯片 8 / PDF 第 8 页 — DPI-UNAWARE：老软件为什么只画左上角

- 导语：`老软件不是「有 DPI 感知」，而是「没有声明 DPI 感知」；DWM 替它放大。`
- 三栏因果链：
  - `老软件以为` / `1280 × 720` / `DPI-unaware，按 96 DPI 绘制；GDI 从 (0,0) 开始。`
  - `GDI 绘制` → `DWM 在屏幕上` / `放大到 1920×1080` / `用户看到的是合成结果，所以老软件看起来是完整的。`
  - `PrintWindow 不走这条` / `PrintWindow 的 1920×1080 画纸` / `1280×720` / `其余空白` / `CU 拿到：左上 1280×720，其余空白。`
- 三条结论（自上而下）：
  - `DPI 虚拟化是 DWM 在合成时做的位图放大，不是应用的 GDI 绘制。`
  - `所以同一个老软件：屏幕上正常，PrintWindow 里只占左上角。`
  - `整屏 CopyFromScreen 取 DWM 输出，因此也不会遇到这个问题。`

### 幻灯片 9 / PDF 第 9 页 — NORMALIZATION：CU 的补偿：把左上角还原成完整画布

- 前提（关键限定）：`只对已验证的 DPI-unaware 窗口做定点归一化，不是通用放大。`
- 示意图（左原始 → 中操作 → 右结果）：
  - 左：`PrintWindow 原始画布 1920×1080` / `1280×720`（只占左上）/ `其余空白`
  - 中：`裁左上 + 放大`
  - 右：`归一化后 1920×1080` / `内容填满` / `后续截图/点击都用这个表面`
- 四个参数格：
  - `awareness = 0` / `DPI-unaware`
  - `DPI = 144` / `150% 显示器`
  - `sourceW/H` / `1920×96/144 = 1280`
  - `缩放` / `1280×720 → 1920×1080`
- 触发条件与兜底：
  - `触发条件：awareness = 0 且类名为 MainWindow / WindowsForms10.*。`
  - `其它 unaware 窗口不盲目裁剪；优先改用整屏模式。`

### 幻灯片 10 / PDF 第 10 页 — DECISION MATRIX：什么时候会出问题：2×2 矩阵

- 导语：`同一个老软件，整屏正确，绑定才需要归一化；问题不在 PMv2 本身。`
- 2×2 矩阵：

  | 目标应用 \ 截图 API | CopyFromScreen（整屏） | PrintWindow（绑定） |
  | --- | --- | --- |
  | PMv2 新软件 | DWM 输出，已按物理像素合成<br>正确 | 应用自己画满物理画布<br>正确 |
  | DPI-unaware 老软件 | DWM 已经把它放大<br>正确 | 只画逻辑尺寸，左上角<br>需要归一化 |

- 三条注解：
  - `红色风险点：物理画纸 + 逻辑画笔。`
  - `PMv2 只改变调用者的测量方式，不改变目标应用怎么画。`
  - `所以「整屏正确、绑定异常」不是矛盾，而是两条路径取的不是同一层。`

### 幻灯片 11 / PDF 第 11 页 — TRADE-OFF：如果 CU 不用 PMv2，会怎样？

- 导语：`PMv2 不是「让老软件变正确」的开关，而是统一物理坐标的选择。`
- 左右反事实对照：

  **用 PMv2（现状）**
  - `GetWindowRect = 1920×1080`
  - `Bitmap = 1920×1080`
  - `老软件只画左上 1280×720`
  - `→ CU 做归一化`
  - `整屏/绑定/点击共用物理坐标`

  **不用 PMv2（反事实）**
  - `GetWindowRect = 1280×720`
  - `Bitmap = 1280×720`
  - `老软件正好画满，没有左上角问题`
  - `但整屏/坐标被虚拟化为逻辑尺寸`
  - `和 2560×1440 物理屏幕不是一套数`

- 结论：`CU 选择前者：统一物理坐标，代价是对 DPI-unaware 老软件做定点归一化。`

### 幻灯片 12 / PDF 第 12 页 — SUMMARY：结论：把三层分开，就不会再混淆

- 导语：`记住三句话，再记住一个边界。`
- 三句话：
  - `① 物理像素是唯一真值` / `图像缩放是第二层；比例用 displayWidth / imageWidth，不是 DPI 1.5。`
  - `② 整屏取 DWM 输出` / `CopyFromScreen 拿最终合成结果；老软件已经被 DWM 放大。`
  - `③ 绑定取窗口绘制` / `PrintWindow 让窗口自己画；PMv2 是尺子，不是取图。`
- 边界（原文措辞即「不承诺通用解决」）：
  - `边界（不承诺通用解决）`
  - `其它 DPI-unaware 窗口、system-aware 跨不同 DPI 屏幕、独占全屏、反作弊/DRM：优先整屏，必要时请用户接管。`
  - `UAC/提权是另一条线，与 DPI 无关；安全桌面永远由用户决定。`
- 收尾：`尺子 · 画笔 · 投影仪`

  - `放大 1.5×` → `归一化后 1920×1080` / `内容填满 1920×1080` / `后续截图/点击都用这个表面`

## 16. 与本次复刻的关系

> 本节是整理者的判断，不是原文。前提：`computer_use_win` 要做的 MCP 需要「DPI 感知 + 窗口/整屏捕获 + 图像坐标→屏幕坐标映射」；目录内已有 `_probe/engine.ps1`（PMv2 + CopyFromScreen + GetWindowRect 原型）与 `_probe/printwindow-test.ps1`（PrintWindow flags 0/1/2 非黑像素采样）。

### 16.1 可以直接采纳（实现时按此落地）

**A. DPI 感知**

1. 进程启动即声明 PMv2：`SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2 = -4)`，且必须在任何 `GetSystemMetrics / GetWindowRect / CopyFromScreen` 之前完成。`_probe/engine.ps1:19` 已是这个写法。
2. 图 14.1 那条「⚠ 做不到 PMv2 就报错，绝不回退到逻辑坐标去猜」应作为硬约束：拿不到 PMv2 就返回明确错误，而不是猜测换算。这条比正文任何一句都重要，因为它把「静默点偏」变成「可观测失败」。
3. 一个进程只声明一次；不要每个请求重设（重复设置行为未定义/可能被忽略）。

**B. 窗口捕获**

4. 绑定捕获 = `PrintWindow(hwnd, memDC, flags)` 到 `Bitmap(GetWindowRect 宽高)`；**每次截图前重新 `GetWindowRect`**（窗口可缩放/最大化/跨屏）。`_probe/printwindow-test.ps1` 已验证 flags `0/2/1` 三条路径并采样非黑像素，可直接扩展成能力探测。
5. 普通窗口的 `GetWindowRect` 含标题栏/边框，客户区更小——MCP 若要让模型点「窗口内某控件」，必须明确返回的是**窗口矩形坐标**（含非客户区），否则会有标题栏高度的系统偏差。
6. 整屏捕获 = `CopyFromScreen` 覆盖**当前显示器物理矩形**，`origin` 取当次显示器 Bounds（副屏可为负）。
7. 归一化只在「已验证 DPI-unaware」时做，且是**定点裁剪+放大**，不是通用放大：`sourceW/H = 物理宽高 × 96 / DPI`（DPI=144 时 1920×96/144 = 1280），再缩放到物理尺寸，之后所有截图/点击都沿用这个表面。

**C. 坐标映射**

8. 只留一个映射函数，两种模式共用，差别只在参数：

   ```text
   screen = round(image × displaySize / imageSize) + origin
   ```

   - 整屏：`displayWidth/Height = 显示器物理尺寸`，`origin = 显示器左上`（可为负）
   - 绑定：`displayWidth/Height = 窗口物理宽高`，`origin = 窗口左上`，**只加一次**

9. 每帧捕获都要把 `imageWidth/imageHeight`、`displayWidth/displayHeight`、`origin` 一起作为元数据返回给上层，且**与像素同帧生成**。原文反复强调「比例用 displayWidth / imageWidth，不是 DPI 1.5」，本质就是禁止任何地方从 DPI 反推缩放。
10. 舍入一律 `round`（§15 已验证 720.88→721、540.66→541；floor 会稳定偏 1px）。
11. 下采样目标：长边 ≤ 1456（2560×1440 与 1920×1080 两种常见表面都会落到 1456×819），并满足 `Ceil(w/28)×Ceil(h/28) ≤ 1568`；`1568×882` 会到 1792，超预算，必须排除。

### 16.2 需要重新验证（不能照抄，必须在目标机上实测）

1. **`PrintWindow` 对现代合成窗口的有效性**：UWP/WinUI3、DirectComposition、Chromium/Electron（GPU 合成）、部分游戏 —— flags 0 常全黑，`PW_RENDERFULLCONTENT(2)` 可能救回也可能仍黑。原文只给了「PrintWindow = 画笔」的模型，没有给「哪些窗口画不出来」的清单。必须用 `_probe/printwindow-test.ps1` 的采样法建立**能力探测 + 自动降级整屏**。
2. **`CopyFromScreen` 的边界**：HDR/广色域、硬件覆盖层（HW overlay）、受保护内容、独占全屏。原文把「独占全屏 / 反作弊 / DRM」列为不承诺区，但没有说明正常窗口在 HDR 下的像素格式/色彩偏移。需实测。
3. **多显示器与混合 DPI**：原文默认「一块 2560×1440」，`origin` 只为副屏负坐标留了一句。需要决定：整屏截「当前显示器」还是「虚拟桌面全部」；不同 DPI 显示器上同一套物理坐标能否拼接。这是原文最大的未覆盖区。
4. **运行期 DPI 变化**：窗口跨屏会触发 `WM_DPICHANGED`，缓存的 rect 立刻失效。原文的「每次重新读 GetWindowRect」是必要不充分的——还需保证「读 rect → 截图 → 生成映射元数据」这一段内不被打断（同一帧原子性）。
5. **类名白名单的可泛化性**：`MainWindow / WindowsForms10.*`（图 14.1 甚至写了 `PopCap`）明显是针对个别老软件的经验值，不能作为产品逻辑。建议改成运行时判定：`GetWindowDpiAwarenessContext(hwnd) == UNAWARE` 且 PrintWindow 内容只覆盖左上 → 归一化；否则降级整屏。
6. **`GetDpiForMonitor`（shcore）偏老**：现代等价物是 `GetDpiForWindow(hwnd)` / `GetDpiForSystem()`，按窗口取更准，也避免枚举显示器。原文用它只是为了说明 144 = 150%，实现时建议替换。
7. **`1456` 这个宽度是模型侧约束**：`Ceil(w/28)×Ceil(h/28) ≤ 1568` 属于服务端图像预处理规则，且服务端可能再缩放一次。需要在真实模型端确认「本地先缩到 1456」是否真的减少 token，还是只是省带宽。
8. **性能数据全缺**：原文没有任何捕获耗时、编码耗时、base64/JSON 体积数据。`_probe/engine.ps1` 已有 `captureMs`、`bytes` 字段，应实测后再定 JPEG 质量（现为 q80）与是否分块传输。当前 `engine.ps1` 把整张图 base64 塞进一行 JSON，大图会有明显的序列化/行缓冲开销。
